# Invariants

> Properties that must ALWAYS hold. A violation is a bug, by definition.
> Scope: behavior that must survive the zimgx (Zig) → imgx (Rust) rewrite. These are the
> spec for TDD during the port — see /Users/christopherw/.claude/plans/recursive-meandering-crescent.md.
> Each invariant names the Zig source it's captured from; the Rust port must have a test
> at the same granularity, not just a manual read-through.

## System invariants

### INV-1: A transform-params cache key is a pure, deterministic function of the parsed parameters, independent of input order

- **Always:** For any two parameter strings that parse to the same `TransformParams` value (regardless of key order in the input string), `toCacheKey` produces byte-identical output. Fields are written in a fixed order: `w, h, q, f, fit, g, sharpen, blur, dpr, rotate, flip, brightness, contrast, saturation, gamma, bg, metadata, trim, anim, frame`. Optional fields at their default/unset value are omitted entirely, not written with a default value.
- **Because:** `src/transform/params.zig:359-383` (`writeCacheKey`) always visits fields in this literal order regardless of parse order, and guards optional fields with `if (x) |v|` / `if (x != default)`.
- **If violated:** Two functionally-identical requests get different cache keys → cache poisoning/duplication. Worse, an existing R2-cached variant (written by the old Zig binary) becomes unreachable under the Rust binary because the key it would compute differs — a silent full cache invalidation of the L2 tier in production.
- **Extended (ThumbHash):** `format=thumbhash` adds one `OutputFormat` value. `to_cache_key()` writes it as `f=thumbhash` in the existing `f` position. No field, field order, or default changes. INV-15 pins this.

### INV-2: Animated-image resize with `fit=cover` never corrupts frame boundaries

- **Always:** When resizing a multi-frame (animated) image with `fit=cover` and both `w` and `h` set, every output frame has identical height (`resized_height`), and `page-height` metadata on the output stack always evenly divides the total stack height. The number of frames in the output never exceeds `min(source_frames, max_frames, 256)`.
- **Because:** `vips_thumbnail_image`'s built-in crop corrupts frame boundaries on vertically-stacked animated buffers (upstream libvips bug #2668). `src/transform/pipeline.zig:212-260+` (resize-without-crop, then either one `extract_area` for horizontal-only crop, or a per-frame crop+`arrayjoin(across=1)` loop capped at 256 frames for vertical crop) is a deliberate, hard-won workaround. Skipping it reintroduces the bug.
- **If violated:** Encoded animated output has visibly wrong/sheared frames, or the GIF/WebP encoder reads past a frame boundary — this exact class of bug previously caused a SIGSEGV (see INV-3).

### INV-3: GIF encoding never receives inconsistent page-height/n-pages metadata

- **Always:** Before `vips_gifsave_buffer` is called on an image carrying `n-pages > 1`, `page-height` metadata evenly divides the image's total height. If it does not, `page-height` is reset to the full image height and `n-pages` is reset to 1 (degrade to a single-frame GIF) before encoding.
- **Because:** `src/transform/pipeline.zig` GIF encode path — a documented regression test reproduces a real prior SIGSEGV in libvips' GIF encoder caused by stale/inconsistent page metadata after cropping.
- **If violated:** Process crash (SIGSEGV) serving a specific animated-GIF transform request — a live availability incident, not just a wrong-output bug.

### INV-4: A request path can never resolve to a filesystem/origin path outside the intended root

- **Always:** `resolve(path)` returns `.not_found` for any path containing a null byte, a literal `..` traversal segment, a percent-encoded traversal/null-byte sequence (`%2e`, `%2E`, `%2f`, `%2F`, `%00`), or an embedded absolute path (`//...`). This holds both for `sanitizePath` called directly and transitively through `resolve`.
- **Because:** `src/router.zig:107-189` (`sanitizePath`, `containsTraversal`, `containsEncodedTraversal`) is the only gate between an untrusted client-supplied path and the origin fetch key / R2 object key.
- **If violated:** Path traversal — the proxy could be tricked into fetching or exposing origin content outside the intended prefix (SSRF-adjacent / origin data exposure).

### INV-5: Every image request uses imgx's fixed `image/<OPTIONS>/<SOURCE-IMAGE>` convention — a fixed prefix, then an OPTIONS segment, then the source path

- **Always:** For a cleaned path, the request must start with the literal prefix `image/`; anything else is `.not_found` (the old trailing-options shape, `/<image-path>/<transforms>`, is retired — this was a conscious, full breaking migration, not an additive route). The segment immediately following the prefix is treated as OPTIONS: if it contains `=`, it is the transform string and everything after it (which may itself contain `/`) is the source image path — unless that remainder is empty, which is `.not_found` (options with no image to apply them to). **Decision:** if that segment does *not* contain `=`, imgx treats it as the start of the image path instead of rejecting the request (relaxing Cloudflare's "at least one parameter" rule, the closest prior art for this URL shape) so a transform-less passthrough request (e.g. `/image/photos/cat.jpg`) still resolves — image path `photos/cat.jpg`, no transform. A path like `image/a=1/b=2` yields transform `a=1`, image path `b=2` — the first segment after the prefix is the only one ever treated as a transform, never a later one.
- **Because:** `crates/imgx/src/router.rs`'s `resolve` (originally ported from `src/router.zig:57-97` with 17 router tests for the old trailing-options shape; migrated to Cloudflare's options-first, fixed-prefix convention as a deliberate breaking change so imgx's canonical URLs are byte-for-byte compatible with Cloudflare's documented format). Tests updated in place to the new shape rather than kept alongside stale old-shape tests.
- **If violated:** URLs stop being interchangeable with Cloudflare's format (defeating the purpose of the migration), or — if the no-`=`-segment passthrough decision above were dropped silently — transform-less requests that used to resolve would start 404ing.

### INV-6: Every `TransformParams` field with numeric or float bounds rejects out-of-range, NaN, and Inf values at parse/validate time — vips never sees an invalid value

- **Always:** `width`/`height` ∈ [1,8192]; `quality` ∈ [1,100]; `dpr` ∈ [1.0,5.0]; `sharpen` ∈ [0.0,10.0]; `blur` ∈ [0.1,250.0]; `brightness`/`contrast`/`saturation` ∈ [0.0,2.0]; `gamma` ∈ [0.1,10.0]; `trim` ∈ [1.0,100.0]; `frame` ≤ 999. Any float parse of `nan`/`inf`/`-inf` is rejected before it can reach `validate()`.
- **Because:** `src/transform/params.zig:314-347` (`validate`) plus `parseF32`'s explicit `isNan`/`isInf` guard at line 471-475. This is the sole gate before values are handed to libvips C calls that do not themselves validate ranges (e.g. a NaN sigma into `vips_gaussblur` is undefined behavior territory).
- **If violated:** Malformed/malicious query strings reach libvips FFI calls with unchecked values — crash or undefined behavior risk at the FFI boundary, not just a bad HTTP response.

### INV-7: Format negotiation priority is fixed and total — it always resolves to a concrete format, never leaves it ambiguous

- **Always (static):** explicit non-auto format always wins outright. Otherwise: alpha-present source → avif > webp > png > jpeg(last resort); no-alpha source → avif > webp > jpeg > png. Empty/absent Accept header → jpeg. **Always (animated):** explicit animation-capable format (webp/gif) wins; explicit non-animation-capable format → `null` (caller must degrade to static); auto-negotiate → webp > gif > `null`.
- **Because:** `src/transform/negotiate.zig:108-185`, 30 tests covering wildcard, q=0 disabling, alpha/no-alpha branches, malformed headers.
- **If violated:** Either a format the client didn't ask for and can't render (broken image in browser), or non-deterministic format selection breaking cache-key/response consistency for identical requests.

### INV-8: The server refuses to start with an invalid configuration rather than running with a partially-bad config

- **Always:** `validate()` rejects (does not clamp or silently ignore): port 0; either timeout = 0; `max_width`/`max_height` = 0; `default_quality` outside [1,100]; HTTP origin with a `base_url` that doesn't start with `http://` or `https://`; R2 origin with any of endpoint/access_key_id/secret_access_key/bucket_originals/bucket_variants empty; `server.max_connections`/`max_request_size` = 0; `cache.max_size_bytes`/`default_ttl_seconds` = 0 when the cache is enabled; `transform.max_frames`/`max_animated_pixels` = 0.
- **Because:** `src/config.zig:203-233` (Zig original) / `crates/imgx/src/config.rs`'s `validate()` (Rust — extended beyond the Zig original's coverage after an audit found several loaded-and-validated-nowhere fields; see INV-11/INV-12 below for two of them). Config is loaded once at startup and validated before the server binds a listener.
- **If violated:** Server starts in a broken state (e.g. no valid origin configured, or a cache/animation limit that silently disables the subsystem it gates) and fails every request at runtime instead of failing fast at deploy time — much harder to diagnose in production (looks like an outage, not a config error).

### INV-9: HTTP error responses always carry the documented status code and JSON envelope shape

- **Always:** Every domain error maps to exactly one of {400, 404, 413, 422, 500, 502, 504} via the named constructors, and serializes to `{"error":{"status":N,"message":"...","detail":"..."}}` with the `detail` key entirely absent (not `null`) when no detail was given.
- **Because:** `src/http/errors.zig` — status codes are fixed per constructor (`badRequest`→400, `notFound`→404, `payloadTooLarge`→413, `unprocessableEntity`→422, `internalError`→500, `badGateway`→502, `gatewayTimeout`→504), and `toJsonResponse` branches on `self.detail` being null to omit the field.
- **If violated:** Callers/clients that pattern-match on the error envelope shape (e.g. checking for absence of `detail` vs. `detail: null`) break; monitoring/alerting keyed on status codes miscounts error classes.

### INV-11: A source image's decoded pixel budget is checked before any resize/effect/encode work touches it

- **Always:** Immediately after the first frame of a source image is probed, `current.width() * current.height()` is compared against `transform.max_pixels`. If it exceeds the budget, the transform is rejected (`TransformError::ExceedsMaxPixels`) before `vips_thumbnail_image`, `vips_thumbnail_source`, any effect filter, or an encoder ever runs on it.
- **Because:** `crates/imgx/src/transform/pipeline.rs`'s `transform()` — `IMGX_TRANSFORM_MAX_PIXELS` was loaded and validated by `config.rs` from the start of the Rust port but never actually read anywhere else, found during a post-launch audit. This is distinct from INV-2/`max_animated_pixels`, which budgets the *total* pixels across an animated stack — INV-11 catches an oversized *first frame* even on a source that turns out not to be animated at all.
- **If violated:** A crafted image with a small compressed size but enormous declared dimensions gets fully decoded into raw pixel memory with no cap — a classic decompression-bomb DoS against server memory.
- **Extended (ThumbHash):** `format=thumbhash` runs after this check. A source over the budget returns `ExceedsMaxPixels` before `thumbnail`, `write_to_memory`, or `encode` runs. INV-20 pins this.

### INV-12: The origin fetcher never buffers an unbounded or over-limit response body into memory

- **Always:** A declared `Content-Length` over `origin.max_size` is rejected before any body bytes are read. A response streamed without (or lying about) `Content-Length` is capped while streaming — accumulated bytes are checked after every chunk, and the fetch aborts the moment the running total exceeds `max_size`, rather than reading the full body first and checking afterward.
- **Because:** `crates/imgx/src/origin/fetcher.rs`'s `fetch()` — the original implementation called `resp.bytes().await` (buffer everything) before ever comparing the length against `max_size`, found during the same audit as INV-11. A compromised or misbehaving origin returning an unbounded body would be fully buffered per in-flight request regardless of the configured limit.
- **If violated:** Unbounded per-request memory growth driven entirely by origin response size — a resource-exhaustion DoS surface independent of anything the client controls.

### INV-13: A failed transform is never cached under the same key a successful transform of the same request would use

- **Always:** When `pipeline::transform()` fails (decode error, unsupported codec, panic) and the server falls back to serving the raw origin bytes, that fallback response is *not* written to the cache. The `cache_key` for a given `(path, transform_string, format)` is only ever populated by an actually-successful transform.
- **Because:** `crates/imgx/src/server.rs`'s `handle_image_request` — the original fallback wrote the raw passthrough bytes to `cache_key` (the same key a successful transform of the identical request would use), so a transient failure (e.g. a brief OOM, a runtime missing a codec plugin — see the AVIF incident that prompted this audit) would poison every subsequent identical request with the wrong (untransformed) response for the full `default_ttl_seconds`, long after the underlying cause recovered.
- **If violated:** A transient, already-recovered failure keeps silently serving wrong output for up to an hour (default TTL) after the fact — the cache actively works against recovery instead of being neutral to it.
- **Extended (Cloudflare parity gap 7, `docs/CLOUDFLARE_PARITY.md`):** an opt-in per-request `onerror=redirect` parameter (`TransformParams::onerror`, matching Cloudflare's own `onerror=redirect`) additively changes the failure-path *response* — a `302` to the origin image URL instead of the raw-bytes fallback, for `Http` origins only. This does NOT weaken the guarantee above: the default (`onerror` unset) behavior is unchanged, and neither the redirect nor the raw-bytes fallback is ever written to `cache_key`. See `crates/imgx/src/server.rs`'s `handle_transform_failure`.
- **Extended (ThumbHash):** for `format=thumbhash`, the server never serves the raw origin bytes. It returns the INV-9 JSON envelope with 422 or 500 instead. It writes nothing under `cache_key`. `handle_transform_failure` stays unchanged for every other format. INV-19 pins this.

### INV-14: An arbitrary attacker-influenced URL is never fetched without every SSRF guard applying, and is never fetched at all unless explicitly opted into

- **Always:** By default (`IMGX_ALLOW_REMOTE_SOURCES=false` and `IMGX_ALLOW_DRAW_OVERLAYS=false`, both defaults), imgx never attempts a network fetch to a URL named in client-controlled request data — a request naming an absolute `http(s)://` source or a `draw[].url` overlay is rejected with `403` before any network call. When either flag is enabled, every fetch through `origin::RemoteFetcher` (`crates/imgx/src/origin/remote.rs`) enforces, unconditionally and together: (1) scheme allowlist (`http`/`https` only, on the initial URL and every redirect target); (2) DNS-resolution-time rejection of non-globally-routable resolved addresses (private/RFC1918, loopback, link-local, RFC6598 CGNAT, `0.0.0.0/8`, multicast, broadcast, and IPv6 equivalents including IPv4-mapped-IPv6 literals), checked *after* real resolution so DNS rebinding cannot bypass it; (3) a separate direct check rejecting literal-IP-address hosts in the same non-globally-routable ranges, since standard HTTP connectors skip DNS resolution entirely for a URL whose host is already an IP literal — the resolution-time check in (2) would never even run for that case; (4) a capped (3), re-validated redirect chain — each hop re-checked against (1)–(3), not just the initial URL; (5) the same streaming size cap as the origin fetcher (INV-12), never buffering an unbounded/over-limit body; (6) the same per-request timeout as the origin fetcher.
- **Because:** `crates/imgx/src/origin/remote.rs` — Cloudflare parity gap 2 (arbitrary remote-URL main-image sources) and gap 11 (draw-overlay remote fetch), both deliberately deferred twice before this implementation specifically because an unguarded fetch of a client-influenced URL is a textbook SSRF vector against internal services (cloud metadata endpoints, internal APIs, other containers on the same host/network). Guard (3) was found during implementation, not designed upfront: hyper's connector (which both `reqwest` and this fetcher build on) shorts-circuits DNS resolution for an already-literal IP host, so a URL pointed directly at e.g. `169.254.169.254` would have silently bypassed a resolution-time-only guard.
- **If violated:** The proxy becomes a confused-deputy SSRF proxy — an attacker who controls a `draw[].url` or a request's source-image segment could make the imgx process issue requests to internal-only services (cloud metadata endpoints, internal admin APIs, other hosts on a private network) that the attacker could not otherwise reach directly, using imgx's network position and any credentials/trust that position implies.
- **Note:** These guards mitigate, but do not eliminate, SSRF risk against internal services when either flag is enabled — they are a defense-in-depth network-layer check, not a substitute for actual network segmentation (firewalling imgx away from sensitive internal services regardless of what the application layer permits). An operator enabling either flag is opting into fetching attacker-influenced URLs; see `apps/docs/src/pages/configuration.mdx` for the operational warning.
- **Extended (ThumbHash):** `format=thumbhash` with a non-empty `draw` fails `validate()` before the 403 draw gate and before any overlay fetch. The format adds no new fetch. INV-20 pins this.

### INV-15: Adding `format=thumbhash` changes no existing cache key

- **Always:** `to_cache_key()` writes `f=thumbhash` only when `format == Some(OutputFormat::Thumbhash)`. It writes the field in the existing INV-1 position. Every literal key in `cache_key_matches_zig_golden_strings` stays byte-identical and unedited. The third `compute_cache_key` segment is `thumbhash` for these requests. The key of a thumbhash request is the same for every parse order of its options. No other field, field order, or default changes.
- **Because:** INV-1 is the compatibility contract with cached R2 variants. The feature adds one enum value and reuses the existing `f=` field. No old request can produce the new string. Before this change, `format=thumbhash` returned 400.
- **If violated:** Every cached variant misses after an upgrade. The origin sees a burst of refetches and retransforms. A thumbhash request can also collide with an image entry and serve the wrong body.

### INV-16: ThumbHash bytes equal the reference encoder byte for byte and are platform independent

- **Always:** `thumbhash::encode(w, h, rgba)` returns the same bytes as `thumbhash@0.1.1` (JavaScript, f64) for every non-degenerate input. A degenerate input is a flat image, an exact gradient, or a symmetric image. Some of its AC terms are zero up to float error. The rounding of a 7.5 tie then decides a nibble, and other implementations disagree on it. Small size alone does not make an input degenerate: the goldens include noise images of 1x1 and 2x7 pixels. It uses f64 in the reference operation order. It calls `libm::cos`, never `f64::cos`. The `disallowed-methods` entry in `clippy.toml` bans `f64::cos`, so `cargo clippy -- -D warnings` fails on any use of it. It reads no clock, no randomness, no environment variable, and no request header. Two calls on the same pixels return the same bytes on every platform.
- **Because:** `crates/imgx/src/transform/thumbhash.rs` holds the port. The Rust `thumbhash` crate (f32) matches only 31 of 48 reference vectors. It matches only 3 of 12 real pipeline outputs. Exact-zero AC terms land on a 7.5 rounding tie, so float noise flips a nibble. `f64::cos` calls the platform libm, so macOS, glibc, and musl can differ. One platform cannot test this rule, because every libm agrees with the goldens there. The lint enforces it on every platform. The hash is an ETag input, so two replicas that share a cache must agree.
- **If violated:** Two replicas or two releases return different bytes and ETags for one URL. Caches disagree. Validators flap. Clients decode a placeholder that differs from the placeholder the reference decoder expects.

### INV-17: The ThumbHash path is total: it never panics and never reads outside its buffer

- **Always:** `thumbhash::encode` returns `Err(ThumbhashError)` unless 1 <= width <= 100, 1 <= height <= 100, and `rgba.len() == 4*width*height`. `rgba_from_bands` returns `Err` unless `bands` is in 1..=4 and `bytes.len() == width*height*bands`. A 16-bit or float buffer therefore fails closed. `VipsImage::write_to_memory` returns `Err(OperationFailed)` when libvips returns a NULL buffer. The strict load of INV-19 makes a source that libvips reports as truncated or corrupt fail at `thumbnail` or at this call. Otherwise it passes the buffer to `save_result` once. `save_result` copies the bytes and calls `g_free` once. Tests cover the NULL path and the length of the copied buffer. No test can observe the single `g_free`. Code structure enforces it: `write_to_memory` has exactly one call to `save_result`, and no other path frees the buffer.
- **Because:** `crates/imgx/src/transform/thumbhash.rs` and `crates/imgx-vips/src/image.rs`. The reference encoder and the `thumbhash` crate `assert!` on a side over 100. libvips computes the buffer length behind the FFI call. Rust must check the length and the sample width itself. A wrong band format read as 8-bit gives garbage colours. The cache keeps the garbage for the whole TTL.
- **If violated:** An out-of-range image panics a worker thread. A non-8-bit image also yields a wrong hash that the cache keeps for `default_ttl_seconds`.

### INV-18: A ThumbHash response body is short base64 text and nothing else

- **Always:** A 200 response for `format=thumbhash` has `Content-Type: text/plain; charset=utf-8`. Its body is 24 to 36 ASCII characters from the standard base64 alphabet, with `=` padding. The body decodes to 17 to 25 bytes. It never contains image bytes, JSON, or markup characters. The result reports the transformed width and height, `is_animated == false`, and `frame_count == None`. The hash landscape bit (byte 4, bit 7) follows the hashed thumbnail, which is at most 100x100 pixels: the bit is set exactly when the thumbnail is wider than it is tall. The thumbnail keeps the order of the sides or makes them equal. So a set bit always means `result.width > result.height`. A result that is only slightly wider than it is tall can have a clear bit. For example, 4000x3999 gives a 100x100 thumbnail. The hash covers the same pixels that every other output format encodes. It ignores the EXIF orientation tag, so `rotate`, `border`, and other steps decide the orientation.
- **Because:** `crates/imgx/src/transform/thumbhash.rs` and `crates/imgx/src/transform/pipeline.rs`. The size bound follows from the ThumbHash layout: luminance at most 7x7, alpha at most 5x5. An opaque image has at least 17 bytes (a long thin image), and an image with alpha has at least 23. The base64 alphabet has no `<`, `>`, or quote, so content sniffing cannot turn the body into markup. The pipeline autorotates only inside a resize. The in-memory thumbnail call sets `no_rotate`, so it never rotates a second time or rotates when no other format would. The landscape check catches a missing or doubled autorotate.
- **If violated:** A client feeds unexpected bytes to the decoder. A proxy can also sniff the body as HTML. The placeholder can also have the wrong orientation.

### INV-19: A failed ThumbHash request never returns origin bytes and never writes the success cache key

- **Always:** When `pipeline::transform()` fails, or its task panics, for `format=thumbhash`, the server returns the INV-9 JSON envelope. Source and libvips failures (`ExceedsMaxPixels`, `Vips`) give 422. `TransformError::Thumbhash` and a task panic give 500. The server never serves the raw origin bytes. It ignores `onerror=redirect`. It writes nothing under `cache_key`. The `detail` key is absent when it is `None`. Failures of every other format keep the existing INV-13 raw-bytes fallback unchanged.
- **Extended (partial decode):** A source that libvips can decode only in part is a failure too. `format=thumbhash` loads the source with `fail_on=error`. `VipsImage::from_buffer_strict` and `VipsImage::from_buffer_animated_strict` do this. `pipeline::transform()` calls them for this format only. A truncated or partly corrupt source then returns `TransformError::Vips`. The server returns 422. The default load uses `fail_on=none`. With it, libvips decodes such a source without an error. The part that libvips cannot decode is blank or partial. Imgx then returns 200 and a hash of blank pixels. For `format=thumbhash`, `resize_reads_source` returns false. The reduced decode reads the source with the default load, so it hides the damage. The resize therefore reads the strictly loaded image. Every other format keeps the default load and the reduced decode, so its output does not change. A strict reduced decode is not an option. `fail_on=error` in the `option_string` argument of `vips_thumbnail_source` is not reliable on libvips 8.15.1. That decode runs in sequential mode. In some runs, a truncated JPEG returned from it without an error. The number of such runs, out of 20, depended on the box size. The result changed from run to run. libvips 8.16.1 and 8.18.4 failed in every run. See the non-invariants below.
- **Because:** `crates/imgx/src/server.rs` (`failed_transform_response` and `thumbhash_failure_response`). One helper handles both failure kinds, so no arm can skip the thumbhash check. `handle_transform_failure` labels raw origin bytes with `tp.format.content_type()`. For thumbhash, the result is a multi-megabyte image labelled `text/plain`. A client would decode image bytes as a hash. A cache write would keep the wrong body for the whole TTL. This extends INV-13 and INV-9.
- **If violated:** Clients receive large binary bodies where they expect 36 characters. A transient failure also poisons the placeholder key until the TTL ends. A hash of blank pixels also stays in the cache for the whole TTL.
- **Note:** `fail_on=error` catches decode errors. It does not catch damage that libvips reports only as a warning. On libvips 8.15.1, a PNG that misses only its last bytes still decodes without an error. A tiny WebP with an intact container and a corrupt bitstream can also decode to blank pixels, and the result changes from run to run, even with `fail_on=warning`. `fail_on=warning` stops on any warning, so it can also reject a valid image. Imgx does not use it. The tests use only sources that fail on libvips 8.15.1, which CI links, and on 8.18.4.

### INV-20: The ThumbHash path is bounded: budget check first, at most 100x100 pixels read out, no new fetch, no new unsafe

- **Always:** Hashing runs only after `first_frame_pixels <= transform.max_pixels` (INV-11). A source over the budget returns `ExceedsMaxPixels` before `thumbnail`, `write_to_memory`, or `encode` runs. The raster copied out of libvips never exceeds 100*100*4 bytes, whatever the source, `w`, `h`, or `dpr`. `format=thumbhash` with a non-empty `draw` fails `validate()` before the 403 draw gate and before any overlay fetch. The status is 422 whether or not `IMGX_ALLOW_DRAW_OVERLAYS` is set. The `detail` says that draw overlays cannot be combined with `format=thumbhash`. `validate()` returns the dedicated `ParseError::DrawWithThumbhash` for this case. The only network fetch is then the source fetch that INV-12 and INV-14 cover. `crates/imgx` keeps `#![forbid(unsafe_code)]`. The ThumbHash code adds exactly one C symbol, `vips_image_write_to_memory`. Only `imgx-vips/src/ffi.rs` declares it. This claim covers the ThumbHash code only. Other features add their own C symbols to `ffi.rs`. The reduced decode adds `vips_thumbnail_source`. Owned source bytes add `vips_blob_copy`, `vips_source_new_from_blob`, and `vips_image_new_from_source`. Loader detection adds `vips_image_get_string`. The operation cache limit adds `vips_cache_set_max`. The tests add `vips_cache_get_max` and `vips_blob_new`. EXIF orientation adds `vips_autorot`. The AVIF effort option adds `vips_heifsave_buffer`. INV-20 does not cover these symbols. The strict load of INV-19 passes `fail_on=error` in the option string of the existing `vips_image_new_from_source` call, so it adds no symbol either. For PNG and JPEG that load reads only the header, so the budget check still runs first. A source that is over the budget and also truncated returns `ExceedsMaxPixels`. The only new dependency in `Cargo.lock` is `libm`.
- **Because:** `vips_image_write_to_memory` materialises the whole raster it receives. On an image that is not downscaled, that is a decompression-bomb read. The overlay fetch is the INV-14 SSRF surface, and a text response discards its result. This feature aims for the smallest attack surface. Automated checks pin that surface, so it does not depend on review memory.
- **If violated:** A crafted image, or a request with `w=8192,h=8192`, forces a large allocation to produce a 30-byte hash. Imgx can also make a pointless outbound request for each placeholder request. A new dependency or `unsafe` block can also enter the audited boundary without a conscious decision.
- **Note:** Three checks have no test. Run them by hand after any change to `Cargo.toml`, `Cargo.lock`, `crates/imgx-vips/src`, or `crates/imgx/src`. First, `git diff Cargo.lock` adds only `libm`, and `cargo deny check licenses bans sources` passes. Second, `grep -rn unsafe crates/imgx/src` finds only the `forbid(unsafe_code)` attributes and comments. Third, `grep -rn write_to_memory crates/imgx/src` finds one call outside tests. It is in `thumbhash_rgba` in `pipeline.rs`. That call is the only place the ThumbHash code reaches `vips_image_write_to_memory`. `thumbhash.rs` has no libvips dependency, and `thumbhash_rgba` calls only the existing `thumbnail` wrapper besides it. The decode step that runs before it uses the symbols of the other features. Ignore those symbols in `ffi.rs` when you run this check.

### INV-21: Resize runs the reduced decode only when the current image equals the decoded source

- **Always:** The resize stage calls `vips_thumbnail_source` on the source bytes only when five things hold. The loader of the probe image is JPEG or WebP. The output is not animated. No earlier stage changed the image. The crop window does not depend on the image content. The format is not `thumbhash`. The earlier stages are the animated reload, the `frame` extract, and `trim`. They also include a per-side trim other than 0, `rotate` other than 0, and `flip`. A parameter whose value leaves the image as it is does not stop the reduced decode. These are `rotate=0` and a per-side trim of exactly 0. `frame` stays a blocker for every value. A content-dependent crop is `gravity=smart` or `gravity=attention` with `fit=cover`, `fit=crop`, or `fit=aspect-crop`. Other fits ignore the gravity. PNG, GIF, AVIF, and animated output always resize the decoded image. `format=thumbhash` always resizes the strictly loaded image (INV-19). `TransformResult::decoded_at_reduced_size` is true only when the resize ran the reduced decode. It does not change the HTTP response.
- **Because:** `resize_reads_source` in `crates/imgx/src/transform/pipeline.rs` and `shrinks_on_load` in `crates/imgx-vips/src/image.rs`. The reduced decode replaces the current image with a new decode of the source bytes. An earlier stage that changed the image is then lost. A reduced decode of a WebP source changes the pixels that `gravity=smart` scores. In the audit, the crop window moved by 4 to 70 px. Before the flag existed, no test saw the reduced decode. Ten mutants of the gate survived. Among them were "optimisation off", "guard inverted", and "PNG takes the source path".
- **If violated:** A `rotate`, `flip`, `trim`, or `frame` request returns the unchanged image. A content-aware crop picks another window than the full decode. A truncated source gives a hash of blank pixels. A PNG, GIF, or AVIF source decodes twice and wastes memory. The optimisation turns off and no test fails.

### INV-22: The pixel budget check runs before any reduced decode of the source

- **Always:** `transform()` compares the pixel count of the first frame with `max_pixels` on the probe decode. That check runs before the resize stage calls `vips_thumbnail_source`. It applies to every output format of a JPEG or WebP source, not only to `thumbhash`. A source over the budget returns `ExceedsMaxPixels`. A source of exactly `max_pixels` pixels passes.
- **Because:** INV-11 and `transform()`. The reduced decode reads the same bytes and the same header as the probe, so it cannot exceed the budget. It also uses less memory than a full decode. A refactor that moves the guard still passes the tests of the other formats. The mutant "skip the budget for a shrinkable source" survived until these tests existed.
- **If violated:** A decompression bomb decodes before the guard runs. A JPEG or WebP over the budget is decoded, not rejected. The memory use of one request has no bound.

### INV-23: The size of a resize does not depend on the decode path

- **Always:** The reduced decode and the full decode give the same width and height for the same source and the same parameters. `fit=contain`, `fit=inside`, and `fit=pad` never exceed the box. For these fits, `resize` compares the size of the reduced decode with `contain_size`. `contain_size` is the size that `vips_thumbnail_image` gives on a full-size image. When the two sizes differ, `resize` decodes again with `size=force` and the exact size. A request whose reduced decode already has the right size keeps its bytes. The size check reads no pixels, except for a source with an EXIF orientation other than 1. There, libvips turns the image in memory during the first call. A corrected request then decodes twice. `fit=cover`, `fit=crop`, `fit=fill`, and `fit=outside` need no correction. They give the same size with both decodes.
- **Because:** `contain_size` and `resize` in `crates/imgx/src/transform/pipeline.rs`. libvips measures the shrink factor on the image that the decoder returns. That image is smaller than the source. After the DCT or WebP scale, libvips computes the residual scale from the rounded size. At a ratio of 4 or more, 10.0 percent of the JPEG requests in the audit differed by 1 px. On typical sources, the difference was 5 px at most. A sweep of 26784 requests found differences of up to 180 px in v0.1.5. They occur when one side of the source is under 10 px. Example: a 4097x5 JPEG with `w=999` gave 999x1 in v0.1.5. The full decode gives 819x1. Example: a 300x225 JPEG with `w=50` gave 50x37 in place of 50x38. `contain_size` follows the libvips maths, including the reciprocal of a reciprocal before the final round. It equals `vips_thumbnail_image` for 9486 combinations of 31 source sizes and 306 boxes. The unit tests pass on libvips 8.15.1, 8.16.1, and 8.18.4. A comparison with the full decode also covered 26358 requests on the fixtures and on generated JPEG and WebP sources. Each request gave the same size with both decodes, or failed with both.
- **If violated:** The same URL returns an image that is 1 px different in size after an upgrade. Layout math, `srcset` checks, and the `pad` border change. `format=json` `width` and `height` change.

### INV-24: The reduced decode never turns a success into a failure, and it agrees with the full decode on damaged JPEG sources

- **Always:** Take a source that the probe accepts. For a damaged JPEG source, the reduced decode and the full decode both succeed or both fail. A WebP source that is cut short fails at the probe with both decodes. For a WebP source with a damaged bitstream, the reduced decode never fails where the full decode succeeds. Both decodes fill the rows that libvips cannot decode from a cut JPEG with gray. `format=thumbhash` keeps the strict decode of INV-19.
- **Known exception:** On libvips 8.15.1, a WebP source with a damaged bitstream can pass the reduced decode and fail the full decode. The unit test found this for all 16 such sources with `w=100`. It found no case with `w=300,h=200,fit=cover`. libvips 8.18.4 fails with both decodes. The reduced decode is then more tolerant than the full decode. It returns a 200 response. Before the reduced decode, the same request failed. The cause is not known. This exception is why the invariant does not claim the same class for every WebP source.
- **Because:** The audit ran 960 requests on 240 damaged JPEG and WebP sources. 666 succeeded with both decodes. 294 failed with both. None was mixed. The audit sources differ from the sources of the unit test. The unit test runs on the libvips version that CI links. It found the exception above.
- **If violated:** One URL returns 200 with one decode and an error with the other. A cache then holds a partial image under the success key.

### INV-25: Colour, alpha, orientation, and metadata do not depend on the decode path

- **Always:** The reduced decode and the full decode give the same container metadata for every output format and every `metadata` mode. That covers the ICC profile bytes, the EXIF segment, and the other ancillary chunks. Both decodes apply the EXIF orientation once. The output carries no orientation tag other than 1. Both decodes keep the alpha channel of a WebP source. Both decodes give a 3-band sRGB image for a CMYK JPEG. The pixel values can differ only by resampling.
- **Because:** The audit compared 504 jobs on 14 files. It found no difference in the ICC hash, the orientation tag, the Copyright tag, the EXIF tag set, or the XMP presence. Nothing pinned this before. A change of a loader option can break it with no test failure.
- **If violated:** A JPEG or WebP resize shows a colour shift, a double rotation, or a lost alpha channel. It can also lose or change the ICC profile, or keep a stale orientation tag.

### INV-26: Source bytes given to libvips are owned copies and are released once

- **Always:** Every libvips source that imgx builds from bytes owns a copy of them, made with `vips_blob_copy`. The image outlives the buffer of the caller. `OwnedSource::from_blob` releases the reference of the caller to the blob. Dropping the `OwnedSource` releases the source. The blob is then freed exactly once. The `imgx` crate never builds a libvips source over borrowed memory. An empty slice fails with the message `empty source` before any copy. `init` sets the libvips operation cache limit to 0. A finished operation then does not keep its input image, or the blob of that image, alive. The server shares the origin bytes with the transform task through an `Arc`. It takes them back for the raw-bytes fallback (INV-13) without a copy.
- **Because:** `OwnedSource` and `init` in `crates/imgx-vips/src/image.rs`, and `reclaim_source` in `crates/imgx/src/server.rs`. INV-20 lists the C symbols. The outlives tests catch the borrowed-memory mistake. The mutants "blob never released" and "source never released" leak memory on each request. They survived until the blob-release test existed. libvips keeps 100 operations by default. Every request builds its operations from new images, so a cached operation never hits again. It only keeps the blob alive. See the non-invariants below for the measured effect.
- **If violated:** A use after free when the caller drops the source bytes. Or a memory leak that grows with each request. Or a peak memory use that grows with the size of the source bytes. Up to 100 operations keep their blobs. Or a log line with no reason for an empty origin body.

## Assumptions & non-invariants

- **Encoded output bytes are NOT invariant across the rewrite.** libvips encoder versions differ, and Wyhash→xxh3 changes the ETag. Parity testing (plan phase 8) compares status codes, headers, cache keys, and image *dimensions* — never raw output bytes.
- **The 256-thread-pool / atomic-connection-counter backpressure mechanism is NOT preserved as-is.** The approved plan deliberately replaces it with an async `tokio`/`axum` model using a `Semaphore` gated on `spawn_blocking` permits. The *invariant* that survives is "the server rejects new work under saturation rather than unbounded-queueing it," not the specific mechanism.
- **`allocator.zig`'s `RequestArena`, R2Cache's "last-fetched-buffer" ownership hack, and threadlocal error-formatting buffers are Zig-specific workarounds, not invariants.** They exist because of Zig's manual memory management; Rust's ownership model makes them unnecessary. Do not port them — porting a workaround whose underlying problem no longer exists is itself a bug (unnecessary complexity, and a plausible source of new bugs).
- **Cache-key byte-for-byte preservation (INV-1) is a policy choice, not a law of nature** — the approved plan chose to preserve it so existing R2-cached variants remain valid across the binary swap. If that decision is ever revisited (e.g. deliberate cache-busting rewrite), INV-1 is the invariant to explicitly relax, and it should be a conscious, documented decision, not a side effect of a refactor.
- **Resize decodes JPEG and WebP sources at reduced size when no earlier stage changes the image (INV-21).** A static request calls `vips_thumbnail_source` on the source bytes. It must have no `trim`, no `trim.*` other than 0, no `rotate` other than 0, no `flip`, and no `frame`. libvips then decodes JPEG and WebP at reduced size. PNG, GIF, AVIF, and animated output call `vips_thumbnail_image` on the full-size image. The two decodes do not give the same pixels. These differences are known, and none of them is an invariant:
  - **JPEG pixels.** libvips scales in the DCT domain only when the shrink ratio is 4 or more. Below 4, the two decodes give the same bytes in almost every request. In rare cases they differ by 1 level at most. Example: a 1201x801 JPEG with `w=640,h=512,f=png` has a ratio of 1.88. The output size is the same. The mean pixel difference is 0.000239 level. The audit found one such request in 24 `f=png` contain requests below a ratio of 4. A width sweep of 214 requests on 5 sources found none. At a ratio of 4 or more, the pixels differ slightly. The median PSNR against the full decode was 44 dB.
  - **WebP pixels.** libvips uses the libwebp scaler in place of the Lanczos kernel at every ratio above 1. This is a filter change, not a rounding change. The audit measured 30 to 40 dB PSNR on detailed sources.
  - **Dimensions.** The size is the same with both decodes (INV-23). Release v0.1.5 gave a size 1 px away from the full decode for some `fit=contain`, `fit=inside`, and `fit=pad` requests. The next release corrects it.
  - **Smart crop.** `gravity=smart` and `gravity=attention` with `fit=cover`, `fit=crop`, or `fit=aspect-crop` decode at full size (INV-21). The window is the window of the full decode. These requests do not get the memory gain of the reduced decode. Other gravities keep it.
  - **Derived output.** `format=json` `file_size` follows the encoded pixel bytes, so it changes with them. `format=thumbhash` never runs the reduced decode (INV-19), so its bytes do not change.
  - **Cost of `format=thumbhash`.** A JPEG or WebP source with `w` or `h` decodes at full size for this format. A trial build with a reduced decode measured the gain on macOS with libvips 8.18.4. An 8000x6000 WebP with `w=400` peaked at 26 MB in place of 596 MB. It took 43 ms in place of 128 ms. A 6000x4000 JPEG with `w=400` peaked at 35 MB in place of 129 MB. It took 12.6 ms in place of 36.8 ms. The gain needs a strict reduced decode. That decode is not reliable on libvips 8.15.1. `fail_on=error` in the `option_string` argument of `vips_thumbnail_source` let a truncated JPEG through in some runs. Take a box of 100x100 on a 2000x1500 JPEG cut at 3/10 of its length. 15 of 20 runs returned a raster in place of an error. The result changes from run to run, so INV-19 fails at random. libvips 8.16.1 on Alpine failed in all 20 runs of every case. So did libvips 8.18.4 on macOS. Revisit this when the oldest supported libvips is 8.16 or later.
  - **Gain.** The audit measured a peak memory use that is 1.4 to 12 times lower. The wall time is 1.15 to 1.4 times better for a JPEG at a ratio of 4 or more. The audit ran each request in a fresh process on macOS with libvips 8.18.4. On that host, a WebP source peaks higher from the second request on in one process. A 24 MP source with `w=400` peaked at 27 MB for the first request and at 212 MB from the second. The full decode peaked at 442 MB. Release v0.1.5 does the same. The cause is not known. Ubuntu 24.04 with libvips 8.15.1 does not show it. There, 60 requests peaked at 61 MB.
  - **JPEG below a ratio of 4.** The audit saw a baseline JPEG at 3 to 15 percent slower in wall time on an idle macOS host. The peak memory use was still lower. A later measurement ran on Linux in Docker, on an Apple silicon host with 16 CPUs. Each cell ran in three blocks of 25, 45, and 45 interleaved calls. The cells were an 8 MP and a 24 MP baseline JPEG at `w=1600` and `w=1000`. Three of these cells are below a ratio of 4. The reduced decode was 1.2 to 6.1 percent slower on Ubuntu 24.04 with libvips 8.15.1. The median was 4.2 percent. It was 1.0 to 7.0 percent faster on Alpine 3.22 with libvips 8.16.1. The median loss on Linux is below 5 percent, so imgx keeps the reduced decode for every ratio. At a ratio of 6, the 24 MP JPEG was 1.9 times faster on both hosts.

  The INV-11 budget check still runs first, on the probe decode (INV-22). `TransformResult::decoded_at_reduced_size` shows which decode ran (INV-21). The tests `resize_reads_source_only_when_no_earlier_stage_changes_the_image`, `jpeg_source_rotate_is_applied_before_resize`, and `jpeg_source_trim_is_applied_before_resize` pin the gate. The bytes and ETags of a variant also change for an unchanged cache key. See the next bullet.
- **A release that changes output bytes changes ETags for unchanged cache keys.** The cache key holds no imgx version (INV-1). No cache tier enforces a TTL. `created_at` is stored, but no code compares it with a TTL. `IMGX_CACHE_DEFAULT_TTL_SECONDS` only sets `Cache-Control: max-age`. A variant in the L2 bucket therefore stays until a lifecycle rule or a purge removes it. The ETag is a hash of the first 8192 bytes of the output, so new bytes give a new ETag. Replicas of two versions that share one L2 bucket can serve either variant for one key. The last writer wins. During that time, a revalidation with `If-None-Match` can return 200 in place of 304. This applies to every release that changes output bytes, for example v0.1.5 and its reduced decode. Drain the old replicas, use a new variants bucket, or expire the old objects. See "Upgrades and cached variants" in `apps/docs/src/pages/deployment.mdx`.
- **A `VipsImage` owns a copy of its source bytes.** `VipsImage::from_buffer` and `VipsImage::thumbnail_buffer` copy the input into a libvips blob. A decoded image therefore never reads freed memory, whatever the caller does with the slice. The copy costs one `memcpy` of the compressed bytes per decode. The copy cannot go. A libvips image reads its source lazily, after the caller can drop the slice. The tests `from_buffer_image_outlives_its_source_bytes` and `thumbnail_buffer_image_outlives_its_source_bytes` overwrite the slice, then encode the image.
- **A request holds few copies of the source bytes (INV-26).** libvips keeps none after the request ends. The server owns the origin bytes once. Before, `handle_image_request` also cloned them for each transform. The clone lived until the transform ended. Each libvips decode adds one blob. A JPEG or WebP resize decodes twice, so it adds two blobs. In a resize, the blob of the probe image drops before libvips reads any pixel.
  - **Operation cache.** libvips keeps up to 100 operations by default. Each one keeps its input image and the blob of that image. Imgx builds every request from new images, so a cached operation never hits. `init` sets the limit to 0. `init_turns_off_the_operation_cache` reads the limit. The memory effect comes from measurements. It is not a test.
  - **Ubuntu 24.04, libvips 8.15.1, Docker.** The harness called `transform()` with jemalloc as the allocator. It ran 5 interleaved pairs and used the median. A 20 MB JPEG of 6000x4000 pixels with `w=400` peaked at 339 MB in place of 134 MB. This was after 25 requests in one process. With 4 parallel threads it peaked at 667 MB in place of 436 MB. A 4.4 MB JPEG of 24 MP peaked at 155 MB in place of 109 MB. Requests per second changed by at most 1 percent (7.9 and 7.9, 29.8 and 29.5, 26.2 and 26.0). The peak of a WebP source did not change.
  - **macOS, libvips 8.18.4, release server.** The test sent sequential requests with a new `w` each. The cache was off. Both changes of this bullet ran together. 40 requests for the 20 MB JPEG peaked at 289 MB in place of 139 MB. They took 5.09 s in place of 5.13 s. 60 requests for the 4.4 MB JPEG peaked at 128 MB in place of 82 MB. They took 2.16 s in place of 2.35 s. 40 requests for a 24 MP WebP peaked at 221 MB in place of 220 MB. Each value is the median of 3 runs.
  - **Clone.** `Arc` and `reclaim_source` remove the clone of the origin bytes. On Ubuntu, the 20 MB source peaked at 154 MB with the clone and at 135 MB without it. That is one copy of the source. The saving grows with the source, up to `IMGX_SERVER_MAX_REQUEST_SIZE`.
